# zvrtsh

«Завертыш» — игра для компании от 2 до 8 человек, в которой игроки отвечают
на вопросы друг друга, видя лишь начало вопроса.

## Как играть

У каждого игрока свой лист. На каждом шаге каждый игрок:

1. пишет вопрос — полный и короткое видимое начало, например «Что?», — и
   загибает лист;
2. получает чужой лист, видит только начало вопроса, отвечает на него вслепую
   и загибает ответ.

Когда все написали вопросы, листы перемешиваются и случайно раздаются заново,
причём никому не достаётся свой лист; вдвоём игроки просто меняются листами.
После ответа лист остаётся у игрока: следующий вопрос он пишет на том же листе.

Когда все шаги пройдены, листы разворачиваются, и становится видно, что
получилось: «Что я ел на завтрак? — Пуговицы».

Во фронтенде: зарегистрируйтесь, выберите число шагов, создайте партию и
отправьте друзьям ссылку или код. Кто открыл ссылку, попадает в комнату
ожидания, а создатель видит, кто уже присоединился, и в любой момент нажимает
«Начать партию» — нужен хотя бы ещё один игрок, всего до 8. Если надоело,
любой может предложить закончить: когда согласны все, партия доигрывается до
конца текущего шага и листы разворачиваются. Ходы других игроков появляются
сразу: их присылает сервер по WebSocket. У каждого игрока свой цвет чернил.

## Структура

```
api/openapi.yaml   контракт HTTP API — единый источник для бэкенда и фронтенда
backend/           сервер на Go: gin, Postgres, миграции migrate
frontend/          React + TypeScript + Vite, отдаётся через nginx
docker-compose.yml Postgres, миграции, бэкенд, фронтенд
Makefile           все команды
```

Действия игроков — обычные REST-запросы, а об их результатах сервер сообщает
по WebSocket `GET /zvrtsh/api/v1/events`: после авторизации внутри сокета он
присылает обновлённую партию каждому из игроков. Протокол описан в том же
контракте (`subscribeEvents`, схемы `EventsAuthMessage` и `EventsServerMessage`).
Если сокет недоступен, фронтенд переподключается с нарастающей паузой, а пока
связи нет — опрашивает REST.

Код по контракту генерируется для обеих сторон: Go-типы и интерфейс
хендлеров ([oapi-codegen](https://github.com/oapi-codegen/oapi-codegen)) в
`backend/internal/ports/httpserver/api`, TypeScript-типы
([openapi-typescript](https://openapi-ts.dev)) в `frontend/src/api/schema.d.ts`.
После изменения контракта:

```bash
make generate
```

## Запуск

Понадобятся docker и make. Сначала создайте `.env` и задайте в нём пароль
базы данных:

```bash
cp .env.dist .env
```

### Всё сразу

```bash
make run-all
```

Поднимаются Postgres, [migrate](https://github.com/golang-migrate/migrate)
применяет миграции из `backend/migrations`, затем стартуют бэкенд и фронтенд:

- игра: http://localhost:3000
- API: http://localhost:8080/zvrtsh/api/v1

Чтобы сыграть с самим собой на одном компьютере, откройте игру во второй
вкладке по адресу http://127.0.0.1:3000 — у неё своё хранилище, и там можно
войти вторым игроком.

### Только бэкенд

```bash
make run-back
```

Postgres, миграции и сервер в docker, API на http://localhost:8080.
Без docker для самого сервера (нужен Go 1.26, база остаётся в docker):

```bash
make dev-back
```

### Только фронтенд (dev-сервер с hot reload)

Нужен Node.js 22+. Бэкенд должен работать на :8080 (`make run-back` или
`make dev-back`), dev-сервер проксирует к нему `/zvrtsh/api`:

```bash
make run-front
```

Фронтенд откроется на http://localhost:5173.

### Остальные команды

`make help` выводит все:

| Команда                        | Что делает                                       |
|--------------------------------|--------------------------------------------------|
| `make generate`                | генерация кода бэкенда и фронтенда из контракта  |
| `make test`                    | все тесты бэкенда и сборка фронтенда с проверкой типов |
| `make test-back`               | тесты бэкенда, включая тесты на Postgres         |
| `make test-unit`               | тесты бэкенда без базы (тесты на Postgres пропускаются) |
| `make migrate-up`              | применить миграции                               |
| `make migrate-down`            | откатить последнюю миграцию                      |
| `make migrate-create name=...` | создать новую миграцию                           |
| `make stop`                    | остановить контейнеры (данные БД сохраняются)    |

## Конфигурация

`backend/config/config.yml` — адреса HTTP-сервера и БД, время жизни инвайта
(`invite-ttl`) и сессии без активности (`session-ttl`). Любое значение можно
переопределить переменной окружения: `users-db.host` → `USERS_DB_HOST`.
Пароль БД — `USERS_DB_PASSWORD` из `.env`.

## Хранение данных

Всё хранится в Postgres, перезапуск бэкенда партии не прерывает. Схема —
миграции в `backend/migrations`:

| Таблица    | Что хранит                                                        |
|------------|-------------------------------------------------------------------|
| `users`    | игроки: имя, хеш пароля, токен                                    |
| `sessions` | партии: число шагов, начата ли, код приглашения и его срок (`invite-ttl`), версия, время последнего хода |
| `session_players` | игроки партии в порядке входа (0 — создатель) и их голоса за досрочное завершение |
| `steps`    | шаги листов с раздачей: кто пишет вопрос (`asker`) и кто отвечает (`answerer`); строки появляются при старте, тексты пусты, пока не написаны |

Изменения партии идут в транзакции с блокировкой её строки, поэтому
одновременные ходы не перетирают друг друга. Партии без ходов дольше
`session-ttl` удаляются вместе с шагами.

Тесты на Postgres (`backend/internal/repo/postgres`) работают с отдельной базой
`zvrtsh_test` в том же контейнере: `make test-back` пересоздаёт её, применяет,
откатывает и снова применяет все миграции. Без переменной `TEST_DATABASE_URL`
эти тесты пропускаются.

В памяти сервера осталась только рассылка событий по WebSocket, поэтому бэкенд
рассчитан на один экземпляр.
